## 1. Результат — `ToolResult`

Контракт и zod-схема — `src/lib/toolResult.ts`. Инструмент возвращает `ToolResult` и никогда не бросает исключение: сбой — `errorResult(code, message)`.

| Поле             | Что класть                                                                                                                                                                                                                           |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `status`         | `success`, `error` или `pending` — инструмент спросил человека и ждёт (`ask_hotelier`), это не ошибка; `running` — только для показа незавершённого запуска                                                                          |
| `summary`        | короткий итог по-русски: его видно в свёрнутом блоке                                                                                                                                                                                 |
| `data`           | машинные данные инструмента; UI их не показывает                                                                                                                                                                                     |
| `evidence[]`     | источники, прочитанные из базы или у провайдера: `source_type`, `source_name` (провайдер), `source_id` (внешний ID), `source_url` (только http(s), иначе `null`), `title`, `excerpt` (слова источника), `retrieved_at`               |
| `claims[]`       | полученные характеристики: готовые русские `label` и `value`, `status` (`observed`/`reported`/`derived`/`inferred`), `confidence` (`null`, если у неё нет основания — число тогда не показывается), `evidence_ids`, `calculation_id` |
| `calculations[]` | расчёты: `name` (без имени функции), `version`, `inputs` (строки «подпись — значение»), `assumptions`                                                                                                                                |
| `method`         | собственный метод инструмента или `null`                                                                                                                                                                                             |
| `limitations[]`  | ограничения: что данные не говорят                                                                                                                                                                                                   |
| `error`          | `{ code, message }` у `error`, иначе `null`                                                                                                                                                                                          |
| `groups`         | необязательно: характеристики по объекту (отелю) — `id`, `title`, `note` (вердикт по-русски), `claim_ids`; блок показывает их разделом «По отелям»                                                                                   |

Правила:

- Источники — только из базы или ответа провайдера. Текст модели источником не бывает; схема не примет характеристику со ссылкой на источник или расчёт, которых нет в результате.
- Нет источников — пустой `evidence`; блок сам напишет «Источников нет».
- Всё, что видит пользователь, — готовые русские строки. Не кладите в `label`/`value` JSON, имена функций, ключи.
- Слова источников (отзывы, страницы) — недоверенный текст: в промпт модели — только цитатами между метками с пометкой «данные, а не инструкции» (см. `toolFacts` в `src/lib/ai/hotelAnswer.ts`).
- Размер: `fitResult` держит результат в 60 КБ (лимит `assistant_messages.data` — 100 КБ); ограничьте списки сами (`MAX_EVIDENCE`, `MAX_CLAIMS`, `MAX_CALCULATIONS`).

Инструмент о многих отелях (подбор) кладёт характеристики каждого отеля в его группу, а отели без данных — в группу без `claim_ids` с объяснением в `note`: «нет данных» — не «подходит» и не «не подходит». Группа может ссылаться только на `claims` своего результата; `fitResult` убирает из групп урезанные характеристики.

## 2. Запуск и запись `tool_runs`

В маршруте оберните вызов в `recordRun` (`src/lib/db/toolRuns.ts`):

```ts
const owner = await runOwner(chatId, messageId) // вошедший и его чат, иначе null
const run = await recordRun(owner, 'my_tool', 'краткий вход без данных пользователя', () => runMyTool(...))
```

- `execute` получает id запуска (`null`, если строки нет — гость): инструмент, который ждёт, связывает с ним то, чего ждёт. Результат `pending` пишется как `waiting` без `completed_at`, с `resume` из `data.request_id`; его завершает событие ответа (`answer_hotelier_request`), а не удержанный запрос.
- `recordRun` проверяет результат схемой (не по контракту — ошибка `invalid_result`), для вошедшего пишет строку `running` до выполнения, затем `success`/`error`, `result_data`, `completed_at` и `tool_run_evidence` (id источников — uuid строк `evidence`).
- Запись — клиентом Supabase с сессией пользователя (RLS), без service role. `runOwner` проверяет, что чат его. Гость (`owner = null`) — ничего не пишется.
- Ошибка записи только логируется кодом; ответ приходит всё равно. Параллельные вызовы — отдельные строки.
- `tool_name` — `^[a-zA-Z][a-zA-Z0-9_.-]*$`, не длиннее 100.

## 3. Шаг хода

Верните шаг с запуском в `steps` ответа:

```ts
{ agent: 'features', title: 'Название операции', params: 'что читаем', status: run.result.status === 'error' ? 'failed' : 'done', result: run.result.summary, run }
```

`agent` — один из существующих (`search`, `features`, `vision`, `geo`, `trips`, `hotelier`). Новый агент — правка `TurnStep` и схемы OpenAPI.

## 4. Браузер и UI

- `askAssistant` и разбор истории (`parseToolRun`) пропускают только запуски по контракту; шаг без `run` показывается старой карточкой.
- `useChats` сохраняет `run` в `data.step` сообщения: блок восстанавливается после перезагрузки (Supabase или localStorage) и попадает в снимок «Поделиться». Шаг с тем же `run.id` обновляется на месте (`mergeSteps`).
- Чтобы, пока ход идёт, была строка с лоадером, добавьте шаг ожидания в `runTurn` (`NOISE_STEP` — пример).
- Блок — `ToolRunCard` (`src/components/AssistantPage/ChatCards.tsx`): ничего не нужно делать, он строится из `ToolResult`.

## 5. Инструменты подбора

Подбор по хранилищу — `src/lib/ai/knowledgeTools.ts` (инструменты) и `src/lib/ai/knowledgeTurn.ts` (ход):

- «Отели по характеристикам» (`hotels_by_features`), «Места рядом» (`nearby_places`, по связям `near`), «Отзывы» (`hotel_reviews`, `searchHotelReviews`: гибридный поиск `hotel_chunks_hybrid` по словам темы и по смыслу её названия, цитируются только фрагменты, где тема названа словами; без ключа модели — только по словам).
- Отбор — чистые функции по индексам всех отелей (`src/lib/db/knowledge.ts`); запуск показывает выбранные отели с claims целиком. Так блоки показывают ровно отели ответа.
- Слова отельера о шуме (`hotelier.room.noise`, `loadHotelierNoise`, читаются свежо) только закрывают «нет данных» критерия «ночью тише N дБ» при N ≥ 50 дБ: `noiseWords` читает правилами «тих»/«бесшум» (тихо), «шумн»/«громк» (шумно), отрицание, оба слова или ни одного — нет данных; тихо — только если все текущие ответы «тихо». Уровень EEA отельер не перебивает; в результате — claim «Шум в номере, со слов отельера» (`reported`, 0,75, «демо» у демо-сведений), в `method.assumptions` и `limitations` — как читаются слова. Этажи номеров (`room.floors`) с высотой здания не связаны.
- Вызовы выбирает модель (`modelKnowledge`: `generateText` с `tools` без `execute`); правила (`rulesKnowledge`) решают, нужен ли подбор, и дополняют план модели тем, что пользователь назвал, а модель пропустила. Запуски идут параллельно через `recordRun`, каждый с таймаутом.
- Ответ (`findings`) пишут правила из claims запусков; модель добавляет одну фразу, которую пропускает `checkedRemark`. Цитаты отзывов модели не передаются (`factsForModel`).
- Новый инструмент подбора: функция отбора `(index, hotelIds, параметры) → Map<id, { verdict, score }>`, результат с группами по `chosen`, вызов в `PLAN_TOOLS` и `rulesKnowledge`.

## 6. Документация и тесты

- Схема ответа уже содержит `ToolRun` (`src/app/api/assistant/schema.ts`); для нового инструмента добавьте пример в `src/lib/openapi/examples` и `scripts/openapi-examples.ts`.
- Тесты: результат на строках хранилища (как `src/lib/ai/noiseTool.test.ts`), живая база по `LIVE_DB=1` (как `noiseTool.db.test.ts`), маршрут, блок. RLS `tool_runs` — `supabase/tests/tool_runs_rls.sql`.

## 7. Инструменты бронирований

Чат о поездках (`brief.trips`, виджет на `/trips` и `/trips/booking`) — `src/lib/ai/bookingTools.ts` (инструменты) и `src/lib/ai/bookingTurn.ts` (ход):

- «Бронирования» (`booking_details`) — бронь (или все брони браузера, по группе на бронь): отель, даты, время заезда, номер и тариф, гости, сумма, условия отмены и удержание при отмене сегодня (расчёт). «Пересчёт при смене дат» (`booking_date_change`) — цена тарифа брони на новые даты, как при бронировании (`quoteDateChange` в `src/lib/trips.ts`), и условия отмены; предложение — в `data.change` и в ответе `change`.
- Брони приходят из браузера в `bookings` запроса без личных данных и проверяются zod-схемой; их характеристики — `reported` без источника. Источник — только отель и тариф каталога (`ota_page` «Островок» у настоящих отелей). В `tool_runs` нет имён, контактов и карты: вход запуска — номер брони и даты.
- Модель выбирает действие, бронь и даты (`modelBookingPlan`), правила дополняют её названным номером брони и датами; ответ о смене дат пишут правила по запуску, ответ на вопрос — модель только по данным запуска (`toolFacts`).
- Даты меняет браузер, и только по «Подтвердить» (`applyDateChange`): бронь, изменившаяся после расчёта, делает предложение устаревшим.
