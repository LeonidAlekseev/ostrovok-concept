## Решения

- **Граница.** Сервер: `src/lib/db/catalog.ts` с функциями того же смысла, что `catalogSource` (`loadDestinations`, `loadHotelSummaries`, `loadHotel`, `loadHotels(ids)`, `loadCityHotels`, `loadNewHotels`), но асинхронными. Клиент: данные пропсами от серверной страницы или `GET /api/hotels?ids=`. Синхронный `catalogSource` в клиенте исчезает.
- **Объём.** Сводка отеля (`HotelSummary`) хранится в колонках/`data`; полный отель — `data jsonb`. Читать только нужные колонки: списки и карты — сводки; страница отеля — один полный отель. Не отдавать клиенту весь каталог (~1,9 МБ).
- **Кеш.** Кеш Next 16 (прочитать `node_modules/next/dist/docs/` про `use cache`/`cacheTag`/`cacheLife` или `unstable_cache` — что поддерживает текущая конфигурация) с тегом `catalog`. Страницы отелей остаются быстрыми: пререндер известных `id` при сборке + выдача новых по запросу.
- **Сборка.** На Vercel ключи расшифровываются в `prebuild` (`.env.production.local`), база доступна при сборке. CI сборку не запускает. Локальная сборка без ключей — понятное сообщение «нет SUPABASE_URL: npm run secrets:reveal».
- **Тесты.** Тесты не ходят в сеть: слой данных мокается генератором (`buildCatalog()`), один набор фикстур.
- **Безопасность.** Чтение — anon-ключом под RLS; сервисный ключ только в `db:seed` и ревалидации.

## Как сделано

- **Кеш.** `cacheComponents` в проекте выключен, поэтому `unstable_cache` (тег `catalog`, `revalidate: 3600`). Полные отели кешируются по городу (запись ~60 КБ), а не одним каталогом (~1,9 МБ, у кеша Next предел 2 МБ на запись). Корневой layout читает направления, поэтому все страницы — ISR с `revalidate = 3600`.
- **Ревалидация.** И время жизни (час), и `POST /api/revalidate` с `Authorization: Bearer <SUPABASE_SERVICE_ROLE_KEY>` → `revalidateTag('catalog', { expire: 0 })`. Отдельный секрет не заводим: сервисный ключ и так есть только у сервера и `db:seed`. `npm run db:seed -- --revalidate https://<сайт>` (только https или localhost).
- **Порядок.** «Сначала популярные» и списки направлений зависят от порядка генератора: миграция `20261022130000_catalog_position.sql` добавляет `position` (nullable) в `destinations` и `hotels`, `db:seed` его пишет; чтение — `order(position nulls last, id)`. Новые отели — `isNew` в порядке каталога (совпадает с порядком сидов).
- **Клиент.** Направления (7 КБ) — контекст `CatalogProvider` из layout (`useDestinations`). Главная — новые отели (сводки) и подборки пропсами; подборкам — `TileHotel` (поля карточки, 5 фото). Вайб и звёзды считаются server actions: вайб возвращает только отели (архетип и доли содержат функции, их браузер считает сам), звёзды — `Reading` (простые данные). Результаты поиска и карта отеля — `GET /api/hotels?destinations=`, избранное, поездки, бронь, подтверждение — `?ids=` (один запрос на набор, `fetchHotels` дедуплицирует).
- **Генератор.** `src/lib/catalog.ts` разделён: типы, подписи и помощники остаются, генератор — `src/lib/catalogGenerator.ts` (только `db:seed` и тесты).
- **Ошибки.** `CatalogUnavailableError`; страница — `error.tsx`/`global-error.tsx` с «Повторить», API — 503, ассистент — 503. Ошибка при фоновой ISR-перестройке оставляет прежнюю страницу.
