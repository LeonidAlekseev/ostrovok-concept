## Context

Хранилище (#346, #350) держит claims с уверенностью, связи `near` (места OSM и Островка в 1 км) и фрагменты отзывов; контракт `ToolResult` и блок `ToolRunCard` (#348) показывают один запуск одного инструмента об одном отеле. Подбор отелей (`runTurn`: поиск по смыслу, затем `featuresStep` по `hotel_features`) идёт после полного брифа и должен уложиться в 15 с ответа.

## Goals / Non-Goals

**Goals:** модель сама выбирает инструменты подбора по пожеланию; каждый вызов — блок с данными по отелям, на которых основан выбор; ответ — только из этих данных; работает без модели.

**Non-Goals:** новые таблицы и функции базы, изменение вопросов брифа, звукоизоляция и снижение дБ, поиск мест дальше 1 км (их нет в хранилище).

## Decisions

1. **Отбор отдельно от показа.** Один инструмент не может показать «свои лучшие» отели: ответ — пересечение вызовов. Поэтому отбор делают чистые функции (`featureVerdicts`, `nearVerdicts`, `chooseHotels`) по индексам всех отелей городов, а запуски показывают выбранные отели (до 6) с claims целиком и итоги отбора («подходят 93 из 205; нет данных у 5»). Запуски после отбора идут параллельно и независимо; отзывы ищутся только у выбранных отелей. Альтернатива — последовательная цепочка инструментов — медленнее и показывает в первом блоке отели, которых нет в ответе.
2. **Три вердикта.** `match`, `miss`, `nodata`. Выбираются отели, где все вызовы `match`; если таких нет — где нет ни одного `miss` и есть `match`, с пометкой «данных не хватает». `nodata` никогда не превращается в «тихо» или «аптеки нет».
3. **Индексы через PostgREST, без миграций.** Уровни: claims `noise.lnight.*`, `noise.lday.estimate.*`, `building.height` всех отелей (около 3 тыс. коротких строк); места: связи `near` с claim `nearby.distance` по `method.categories` (OSM и место Островка, совпавшее с OSM) и `method.kind` (Больница, Парк, Пляж Островка); страницы по 1000 строк, кэш каталога на час. Подробности (источники, расчёты) читаются только для выбранных отелей: `loadHotelClaims`, `loadClaimsByIds`, `hotel_chunks_search`.
4. **Порог «тихо ночью».** Самая громкая полоса Lnight по всем источникам EEA заканчивается ниже 50 дБ (полоса 45–49 подходит); модель может назвать другой порог (35–75). «Ниже 40 дБ» хранилища — полоса ниже картирования, это данные, а не их отсутствие.
5. **Выбор вызовов.** Правила (`rulesKnowledge`) решают, нужен ли подбор хранилищем (тихо, место из категорий хранилища кроме пляжа — море остаётся за `seaMaxM`, слово «отзыв»), и дают запасной план. Модель (`generateText` с `tools`, `toolChoice: 'required'`, без `execute`) выбирает вызовы и параметры, пока идёт поиск по смыслу; её высоты 0–300 м отбрасываются как не отбирающие. Время: поиску по смыслу оставляется на 4 с меньше, план модели ≤ 4 с, запуск ≤ 5 с с таймаутом-ошибкой, фраза модели — только если осталось ≥ 2 с.
6. **Ответ правилами.** Как в гео-ходе: текст с фактами строят правила из claims запусков; модель добавляет одну фразу, проверенную `checkedRemark` (нет чисел, единиц, чужих имён). Модель видит факты без цитат отзывов (`«…»`), поэтому недоверенный текст в промпт не попадает.
7. **Группы в контракте.** Необязательное поле `groups` (`id`, `title`, `note`, `claim_ids`) — старые результаты валидны; схема не принимает группу со ссылкой на чужой claim; `fitResult` чистит группы после урезания.

## Risks / Trade-offs

- Кэш индексов на час: новые claims видны после `POST /api/revalidate` или истечения. → Тот же контракт, что у каталога.
- Подбор начинается только при полном брифе: на «Найди отель… аптека и тихо» Эвал сперва спрашивает «когда» и «с кем». → Сохраняем принятый диалог; изменение — отдельным решением.
- Индекс аптек — около 1000 строк, две страницы: первый запрос после сброса кэша дольше на ~1 с.
